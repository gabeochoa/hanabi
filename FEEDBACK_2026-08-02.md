## F1 ROOT-CAUSE INVESTIGATION (messages missing on real data)
Authoritative Navi block schema (from message.list on a real session):
- text block:        {type:"text", content:"..."}                    ← matches hanabi default ✓
- tool_call block:   {type:"tool_call", toolCall:{id,name,inputs,startedAt}}  ← matches ✓
- tool_result block: {type:"tool_result", toolResult:{output:[{text,type}],status,toolCallId,completedAt}}
  ← output is an ARRAY of {text,type}, NOT a string. hanabi reads field_tool_output="output" as a string.
- top-level msg also has a flat "preview" (string) and role user/assistant.

HYPOTHESES (ranked) for "only tool calls, no messages":
1. The REST transcript endpoint hanabi hits (/sessions/{id}/messages) may return a DIFFERENT
   envelope than the message.list ACTION (e.g. text under a different key, or messages nested
   under a "messages" wrapper the adapter doesn't unwrap) → text blocks parse empty → no
   Assistant messages, while tool_call blocks (structurally distinct) still split out. THIS
   MATCHES THE SYMPTOM EXACTLY (tool rows present, text rows absent).
2. tool_result.output is an ARRAY not a string → tool_result parsing may partially work while
   text extraction fails.
NEXT: confirm by pointing hanabi at the real endpoint with HANABI_DUMP=1 and reading the raw
envelope, OR compare /sessions/{id}/messages REST shape vs the message.list action shape.

## BUILD-ARTIFACT HAZARD (process note)
`output/hanabi.exe` is shared: a plain `make` (notls) overwrites a `make HANABI_TLS=1` (tls)
binary in place (different obj dirs, same exe path). A notls binary can't fetch the https
transcript → "requires a TLS build" error that LOOKS like a transcript bug but is a stale exe.
Always rebuild HANABI_TLS=1 before real-backend testing. (Cost me one false lead this session.)
